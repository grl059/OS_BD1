\section*{Хураангуй}
\phantomsection\addcontentsline{toc}{section}{Хураангуй}
\noindent\rule{\textwidth}{1.2pt}\par\vspace{6pt}

Энэхүү эцсийн тайланд БД1-ийн төслийг, өөрөөр хэлбэл Linux \term{kernel}-ийн өгөгдлийн бүтцүүдийг (1.9-д заасан бүх үндсэн бүтэц + \term{red-black} мод, \term{min-heap}, процессын хуваарилагч) C хэл дээр хэрэгжүүлж, команд бүрийн дараах төлвийг веб дээр график хэлбэрээр харуулдаг \code{kds} хэрэгсэл ба \term{kernel module}-ийг II-4-13 ба II-4-9 хоёр багийн албан ёсны шүүмжид тулгуурлан сайжруулсан ажлыг тайлагнав. Шүүмжлэгч хоёр багаас гарсан санал бүрийг Critical, Major, Minor, Suggestion гэж ангилан, 4-р хэсгийн Хүснэгт 4.1 (14 мөр) ба Хүснэгт 4.2 (12 мөр)-т нийт 26 мөрөөр нэг нэгээр нь шийдвэрлэсэнээ харуулав. Гол сайжруулалт гурван чиглэлтэй. Эхнийх нь 16-аас олон үгтэй командад C цөм санах ойн алдаа гарч, веб дээр мэдэгдэлгүй гацдаг байсныг \code{ERR too many tokens} болгон засаж, муу мөрийг скриптээс буцаан, алдааг монголоор тайлбарласан явдал юм. Хоёр дахь нь \code{sched stats} командаар дундаж хүлээлтийг програм өөрөө тооцдог болгож, веб дээр \term{red-black} мод ба \term{min-heap}-ийг нэмж 9 бүтцийг бүрэн дүрсэлсэн явдал юм. Гурав дахь нь \term{kernel module}-ийг жинхэнэ Linux дээр ачаалж баталгаажуулсан явдал юм.

Засварын өмнөх (шүүмжилсэн) болон дараах хувилбарыг ижил тестээр дахин ажиллуулж харьцуулав. Өмнө нь 19 үгтэй \code{list add_tail} мөрөнд \term{ASan} \code{stack-buffer-}\allowbreak\code{overflow} гарч байсан бол одоо \code{ERR too many tokens (max 14 arguments)} гарна. \code{make check}-ийн 98 шалгалт засварын өмнө ч, дараа ч бүгд PASS бөгөөд regression ажиглагдаагүй. Шинэ \code{sched stats} нь гараар бодсон 5.00 (\term{Round Robin}) ба 4.33 (\term{FCFS}) утгыг програмаас шууд гаргадаг. \term{Kernel module} нь Ubuntu 24.04.2 (\term{kernel} 6.11.0-17, \term{Secure Boot} идэвхтэй) дээр \term{MOK} түлхүүрээр гарын үсэг зурагдаж ачаалагдан, автомат тест скриптийн 9 шалгалт бүгд PASS боллоо.

\section*{1. Төслийн тойм}
\phantomsection\addcontentsline{toc}{section}{1. Төслийн тойм}
\hthree{1.1 Зорилго ба хамрах хүрээ}

Үйлдлийн системийн \term{kernel} нь процессын жагсаалт, \term{ready queue}, \term{bitmap} (нөөц чөлөөтэй эсэх), хэш хүснэгт (хурдан хайлт), модон бүтэц (\term{scheduler}, санах ой) зэргийг өгөгдлийн бүтцээр удирддаг. Эдгээр бүтэц нь зөвхөн онолын жишээ биш -- \term{kernel}-ийн найдвартай, хурдан ажиллах чадвар шууд тэдний зөв хэрэгжилтээс хамаардаг тул Үйлдлийн системийн чиглэлээр суралцаж буй оюутан эдгээрийг зөвхөн уншиж ойлгоход хязгаарлагдахгүй, өөрийн гараар хэрэгжүүлж, туршиж, зөв эсэхийг нотолж байж бүрэн эзэмшинэ гэж үзсэн.

\textbf{Зорилго.} Сурах бичгийн 1.9-д заасан бүх үндсэн бүтцийг (холбоост жагсаалт, \term{stack}, \term{queue}, \term{BST}, тэнцвэржсэн мод, \term{hash map}, \term{bitmap}) болон 3-р бүлгийн Processes сэдвийн PCB/ready queue-г C хэлээр, Linux-ийн \code{list_head} семантиктай нийцүүлэн хэрэгжүүлэх, элемент нэмэх, устгах, хайх үйлдэл бүрийн дараах төлвийг график хэлбэрээр нүдэнд харагдуулах. Хэрэгжилтийн зөв ажиллагааг санамсаргүй \term{stress} болон \term{fuzz} тестээр, ASan/UBSan ашиглан системтэй нотолж, сурах бичгийн Programming Project (3-р бүлэг)-ийн дагуу бодит Linux \term{kernel module} бичиж, жинхэнэ \term{kernel} орчинд ачаалан (insmod/rmmod) баталгаажуулна.

\textbf{Ач холбогдол.} \code{list_head} бол Linux \term{kernel}-ийн хамгийн их хэрэглэгддэг бүтэц бөгөөд \code{task_struct} (\term{PCB}), \term{ready queue} зэрэг нь түүн дээр суурилдаг \srccite{4}; үүнийг ойлгох нь 3-р бүлгийн «Processes» сэдвийн суурь болно \srccite{1}. \term{Kernel} дотор ашигладаг \term{intrusive} (өгөгдлийн \term{struct} дотроо холбоос агуулсан) жагсаалтын загвар нь user-space-ийн ердийн жагсаалтаас бүтцийн хувьд ялгаатай тул оюутанд энэ ялгааг гараар хэрэгжүүлж үзэх нь ач холбогдолтой. График дүрслэл нь \term{тэнцвэржсэн}/\term{тэнцвэргүй} модны хайлтын гүнзгийрэлтийн ялгааг, хэш хүснэгтийн \term{collision}-ийн нөлөөг шууд нүдээр харуулдаг.

\textbf{Хамрах хүрээ.} Хэрэглэгчийн орчны загвар (C, \term{CLI}), түүн дээр суурилсан веб хуудас (Next.js), мөн нэг \term{kernel module}. Энэ төсөл нь Linux-ийн жинхэнэ \term{scheduler}-тэй холбогдоогүй. Төсөлд хэрэгжүүлсэн \term{FCFS} (ирсэн дарааллаараа ажиллуулах) ба \term{Round Robin} (процесс бүрт ээлжлэн тодорхой хугацаа өгөх) алгоритмууд нь Linux-ийн бодит CFS \term{scheduler}-ийг орлох зорилготой биш юм. Эдгээр нь зөвхөн сурах бичгийн энгийн загварыг ойлгомжтой харуулахад зориулагдсан.

\hthree{1.2 Сурах бичгийн шаардлага ба БД1-ийн хэрэгжилт}

\textbf{Хуваарилалт:} код 4, «\term{Kernel} Data Structures», үзүүлэлт «\term{Kernel} structure graph», бүлэг 3 -- Processes, F.CSM302 «Бие даалт 1» удирдамжийн дагуу \srccite{5}. Онолын хэсэг нь \textbf{Chapter 1 Introduction-ийн 1.9 \term{Kernel} Data Structures (p. 36)}. \textbf{Хүрэх үр дүн:} «Сурах бичигт заасан \term{kernel} data structure-ийн хэрэглээг хэрэгжүүлж, элемент нэмэх, устгах, хайх үйлдлийн дараах бүтцийг графикаар харуулна.»

Operating System Concepts-ийн 3-р бүлгийн Programming Project «\term{Kernel} Data Structures» нь Chapter 1-ийн 1.9 \term{Kernel} Data Structures (p. 36)-д тайлбарласан бүтцүүд дээр тулгуурласан хоёр хэсэгтэй.

\hthree{1.3 Онолын товч ба нэр томьёо}

\textbf{Эх сурвалж:} Silberschatz, Galvin, Gagne, \textit{Operating System Concepts}, 10th ed., Chapter 1 Introduction, 1.9 \term{Kernel} Data Structures, p. 36 (1.9.1 жагсаалт/stack/queue, 1.9.2 мод, 1.9.3 \term{hash}, 1.9.4 \term{bitmap}) \srccite{1}.

\textbf{\code{list_head}} нь \term{intrusive} (өгөгдлийн \term{struct} дотроо холбогдох талбараа агуулсан), давхар холбоост, дугуй жагсаалт юм. Node нь өгөгдлийн \term{struct} дотор \code{list_head} талбар агуулж, \code{container_of} макро нь талбарын хаягаас эзэн \term{struct}-ийг сэргээнэ. Нэмэх, устгах үйлдэл $O(1)$, хайх нь $O(n)$ \srccite{4}. Зураг 1.1 нь гурван зангилаатай ийм жагсаалтын \code{next}/\code{prev} холбоосыг харуулав.

\textbf{\term{Queue} (\term{FIFO}, First-In-First-Out)} нь tail-д нэмж head-ээс авдаг. \term{Kernel}-ийн \term{ready queue} ийм зарчмаар ажилладаг. \textbf{\term{Stack} (\term{LIFO}, Last-In-First-Out)} нь head-д нэмж head-ээс авдаг \srccite{2}. \textbf{\term{Bitmap}}-д 1 бит нь 1 нөөцийг илэрхийлнэ. set/clear/test нь $O(1)$ бөгөөд Boolean массиваас 8 дахин бага зай эзэлнэ \srccite{1}.

\textbf{\term{Binary search tree} (\term{BST})}-д зүүн $<$ үндэс $<$ баруун байна. Дундаж хайлт $O(\lg n)$, харин эрэмбэлсэн оролтод мод нэг шугам болж хамгийн муу тохиолдол $O(n)$ болно. \term{Тэнцвэржсэн} (\term{AVL}) мод n элементэд ойролцоогоор $\lg n$ түвшинтэй байдаг \srccite{2}. Linux \term{red-black} мод ашигладаг бол бид ижил зорилготой \term{AVL} модоор (өндрийн зөрүү $\le 1$, эргүүлэлт) загварчилсан -- \term{AVL} тэнцвэржилтийн анхны алгоритмыг Adelson-Velsky ба Landis тодорхойлсон \srccite{3}. Зураг 1.2 нь ижил 1--7 оролтод энгийн \term{BST} ба \term{AVL}-ийн өндрийн ялгааг, Зураг 1.3 нь \term{AVL}-ийн нэг зүүн эргүүлэлтийг харуулав.

\textbf{\term{Hash map}}-д хэш функц түлхүүрийг хүснэгтийн индекс болгож, ихэнх тохиолдолд $O(1)$ хайлт өгнө. Хоёр түлхүүр нэг индекст таарвал (\term{collision}) тухайн \term{bucket}-д жагсаалт залгана. \term{Collision} олшрох тусам хайлт $O(n)$ руу ойртоно \srccite{2}.

\textbf{Процесс ба \term{scheduler}.} Процесс бүр \term{PCB} (Process Control Block)-тай байдаг (Linux-д \code{task_struct}). Бэлэн процессууд \term{ready queue}-д зогсоно. \term{FCFS} (First-Come-First-Served) нь процессыг дуустал нь ажиллуулна. \term{Round Robin} нь процесс бүрд квант хугацаа өгч, дуусаагүй бол дарааллын төгсгөлд буцаана. Хүлээлтийн хугацааг нийт үргэлжилсэн хугацаанаас ажлын хугацааг хасаж олно \srccite{1}.

\textbf{\term{Kernel module} ба параметр.} \code{module_param(name, type, perm)} нь \code{insmod kds_module.ko start=15} хэлбэрээр утга дамжуулах боломж олгоно. Init амжилтгүй болбол \code{module_exit} дуудагдахгүй тул init өөрөө нөөцөө чөлөөлөх ёстой. Нийтлэг алдаанууд: \code{list_del}-ийн дараа pointer ашиглах, node чөлөөлөхгүй үлдээх (leak), гүйлгэж байхдаа устгах (энэ үед \code{_safe} хувилбар хэрэгтэй).

Тайланд олон давтагддаг нэр томьёог шинэ уншигч бүр өөрөө хайж олох шаардлагагүй байлгахын тулд Хүснэгт 1.2-д тэдгээрийн энгийн тайлбарыг нэгтгэн оруулав.

\term{Kernel module}-ийг зөвхөн нэг машин дээр (Ubuntu 24.04.2, \term{kernel} 6.11.0-17-generic) ачаалж туршсан; өөр \term{kernel} хувилбарт дахин build хийх шаардлагатай. \term{Secure Boot} идэвхтэй үед гарын үсэггүй модуль ачаалагдахгүй тул \term{MOK} түлхүүрээр гарын үсэг зурсан.

Хэш функц нь энгийн нийлбэр тул «ab», «ba» шиг үсгийн байр солигдсон түлхүүрүүд үргэлж \term{collision} үүсгэнэ. \term{Bucket}-ийн тоо auto resize-ээр 64 хүртэл ихэсдэг ч элементийн хязгаар 24-өөр бүдүүн дүрслэл болгож тоог хязгаарласан.

\term{Scheduler}-т бүх процесс үүсгэсэн мөчдөө ирнэ гэж үзсэн; I/O хүлээлт ба тэргүүлэх эрэмбэ байхгүй. Веб апп зөвхөн дэлгэц дээр зурдаг, өөрөө логик агуулдаггүй тул локал ажиллуулахад \code{make}-аар \code{kds}-г урьдчилан build хийх шаардлагатай. \term{Queue}, \term{stack} ба амьд процессын тоо 8, \term{hash}-ийн элемент 24-өөр хязгаарлагдсан -- энэ нь дүрслэлд багтаах зорилготой.

\textbf{Part I/II-ийн дүрслэл (II-4-9 M-1).} Сурах бичгийн Programming Project-ийн Part I (\code{struct color}) ба Part II (\term{Collatz}, \code{start} параметр) сурах бичигт \code{kmalloc} ба \code{list_head} ашиглан \term{kernel} дотор хийгддэг тул бид жинхэнэ \term{kernel}-д ачаалж \code{dmesg} ба \code{/proc/kds}-оор баталсан (Зураг 6.2--6.4); \code{kds}-д давтан хэрэгжүүлбэл user-space-н давхар хэрэгжилт болж, \code{state}-ийн түлхүүр 9-өөс 11 болж «9 бүтэц» гэсэн бүх нотолгоо эвдэрнэ (дэлгэрэнгүй үндэслэл M-1 мөрт).

\textbf{Шүүмжээс үлдсэн.} Playwright E2E тест, дан холбоост жагсаалтын тусдаа демо нэмээгүй (4-р хэсгийн P2, P10). Manual 2.7-ийн \term{Secure Boot} заавар зураггүй. II-4-9-ийн M-1-ийг дээрх үндэслэлээр граф дээр нэмээгүй; M-2-ын хувьд 6 гишүүний гурав нь тусдаа git идентификаторгүй хэвээр (түүхэн commit-ыг дахин бичээгүй) --- үүнийг Хавсралт A-д нуухгүйгээр тодорхой бичсэн.

\hthree{7.2 Дэмжих орчин}

\term{CLI} ба веб апп нь Ubuntu 24.04 (gcc 13, Python 3.13, Node.js 22) дээр бүрэн туршигдсан; тестийн скрипт Python 3.8-аас дээш хувилбар шаарддаг тул \code{make check}-ийн 98 PASS-ийг II-4-9 баг Python 3.12 орчинд давтан гүйцэтгэсэн. Windows дээр MSYS2 эсвэл WSL ашиглах заавар Manual-д бий боловч энэ тайлангийн туршилтыг Windows дээр хийгээгүй. macOS дээр CI (\term{ASan}-тай) ажилладаг ч macOS 26 дээр \term{ASan} эхлэхэд гацдаг тул \code{make SAN=0} хэрэглэнэ. \term{Kernel module} нь зөвхөн жинхэнэ Linux дээр (\term{kernel} headers-тэй) ачаалагдах бөгөөд WSL ба Docker дээр ачаалагдахгүй.
